  pid  | state  | wait_event_type | wait_event    | pg_blocking_pids | query

                                                                       WHERE customer_id = $2 AND tenant_id = $3

  Direction: 4678 (the reference-publication task) waits on 4677 (the VM-retirement
  transaction, which is COMMITting). 4677 waits on NOTHING ({}). This is a single
  directional wait, NOT a cycle. It resolves the instant 4677 commits — exactly the
  intended "inventory lock wins" ordering the test asserts. No back-edge exists: the
  publication only ever touches customer_tenants; it never waits on vm_inventory.

Also present (same sample) — a pure harness convoy of ~15 backends serialized on a shared
advisory lock during parallel per-schema migration setup:

This convoy is created by many isolated test schemas each running migrations concurrently
against one server and serializing on one advisory lock. Production migrates ONE database
once; it never has this convoy. Every convoy member cleared in the next sample.

HANDLER SOURCE ANALYSIS (why no production cycle is possible)
============================================================================
decommission_vm  (infra/api/src/routes/admin/vms.rs:473)
  -> PgVmInventoryRepo::decommission_if_unreferenced (infra/api/src/repos/pg_vm_inventory_repo.rs:188)
     1. self.pool.begin()                              -- ONE connection, ONE transaction T
     2. SELECT ... FROM vm_inventory WHERE id=$1 FOR UPDATE   (lock_vm_for_retirement :29)
     3. SELECT ... FROM vm_inventory_reference_blockers($1)   (load_retirement_blockers :45)  -- reads customer_tenants
     4. UPDATE vm_inventory SET status='decommissioned' WHERE id=$1 AND status='active'
     5. COMMIT
  The handler uses EXACTLY ONE connection for the whole operation. It never acquires a
  second connection while holding the first. Therefore the test's route pool bound
  pool_in_schema(schema, 1) (admin_vm_retirement_test_support.rs:186,:231) is SUFFICIENT
  for the handler — the "single-connection pool starves the handler" hypothesis is FALSIFIED.
  Lock order within T is linear (vm_inventory row, then customer_tenants read); the
  concurrent publication takes only a customer_tenants row lock and never reaches back to
  vm_inventory, so the two transactions cannot form a cycle. With an unbounded production
  pool the same handler issues the same single-transaction, single-direction lock sequence.

============================================================================
VERDICT
============================================================================
TEST_HARNESS_ARTIFACT

Support: the only serialization observed in the live lock graph is harness-manufactured
(the per-schema advisory-lock migration convoy, the tests' own `LOCK TABLE customer_tenants
IN ACCESS EXCLUSIVE` gate, and the single-connection micro-pools), never a cycle between
statements the decommission handler itself issues. The handler runs a single transaction
with a linear lock order and no back-edge (pids 4677/4678 above: one-way wait, resolves on
commit), so with an unbounded production pool it cannot deadlock. The CI >60s stall is a
contention/starvation property of dozens of schema-isolated micro-pools against one
connection-capped, slower shared server — a harness bound production does not have.

Stage 2 keys its fix location on this verdict: TEST_HARNESS_ARTIFACT ->
infra/api/tests/common/admin_vm_retirement_test_support.rs (the harness), NOT
infra/api/src/routes/admin/vms.rs (the handler).

CAVEAT / PROXY BIAS (per stage step 4/5): the exit-124 >900s hang did NOT reproduce on this
16-vCPU x86 devbox under any of runs A/B/C — the named tests passed every time and no lock
wait ever crossed 6s. The CI specimen is a 4-vCPU GitHub-hosted runner. This verdict rests
on (i) the live lock-graph wait direction above and (ii) the single-transaction handler
source, using the CI log as the specimen and the contended local runs as proxy. Stage 2 must
treat the CI log as the primary specimen and a deliberately contended local run as proxy,
and its bounded-timeout guard (wrapping the helper body in tokio::time::timeout) is what will
turn any residual harness starvation into a bounded, self-naming failure on every platform.
